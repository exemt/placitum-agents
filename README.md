# placitum/agents

Сайдкары наблюдения Placitum: маленькие процессы, которые рассказывают контуру, как себя
чувствует инфраструктура рядом с ними.

Три штуки, каждая своим модулем и своим образом:

| Каталог | Образ | Что делает |
| --- | --- | --- |
| [`redis/`](redis) | `placitum/agents-redis` | здоровье, память и ключи одного экземпляра Redis; кадр присутствия `WAF_STATUS.store.redis.<id>` |
| [`s3/`](s3) | `placitum/agents-s3` | бакеты архива: доступность, размеры, срок; кадр `WAF_STATUS.store.s3.<id>`. Бакеты заводит сам |
| [`haproxy/`](haproxy) | `placitum/agents-haproxy` | не сайдкар, а узел: haproxy с агентом в одном контейнере, конфигурацию ведёт контроллер |

Первые два — наблюдатели: своего состояния не держат, на трафик не влияют, потеря агента не
трогает ни хранилище, ни контур. Третий — балансировщик с управляемой конфигурацией: агент живёт
на самой ноде, потому что `haproxy -c` обязан проверять конфиг тем же бинарём, который держит
трафик.

## Сборка

Каждый собирается из своего подкаталога:

```sh
docker build -t placitum/agents-redis redis
docker build -t placitum/agents-s3 s3
docker build -t placitum/agents-haproxy haproxy
```

Из git — тем же путём, подкаталогом в контексте:

```sh
docker buildx build -t placitum/agents-redis \
  "https://github.com/exemt/placitum-agents.git#develop:redis"
```

Переменные и раскладка — [INSTALL.md](INSTALL.md); устройство каждого — `docs/README.md` в его
каталоге.

## Почему они в одном репозитории

У всех троих один контракт — кадр присутствия на `WAF_STATUS`, — и правятся они обычно вместе:
меняется форма кадра, а не поведение конкретного агента. Три репозитория означали бы три
синхронных правки на каждое такое изменение. Установщику это безразлично: контекст сборки умеет
подкаталог.

## Ветки

`develop` — то, что разрабатывается: сюда приезжает каждая выкладка. `main` — выкаченные сборки.
Правок в этом репозитории не делают: обе ветки производные от платформы.
