# Балансировщик под управлением контроллера

HAProxy перед управляемыми краями и его агент (`agents/haproxy`): haproxy и
агент в одном контейнере, конфигурацию ведёт панель — страница
`/config/haproxy`, рядом с «Общая» и «http».

## Канал

Форма та же, что у настроек агента (`policy/agent-conf`): документ мелкий и не
секретный, поэтому едет в значении ключа KV целиком, без блобов в Redis и без
конвертов. Отличие одно: в KV кладётся не документ настроек, а **собранный из
него `haproxy.cfg`** — применяет нода именно файл, и хеш считается по его
тексту.

```text
Postgres haproxy_settings ──рендер──▶ haproxy.cfg ──send──▶ KV policy/haproxy-conf
                                                                 │ watch
                                              агент: haproxy -c ─┴─▶ подмена файла ─▶ SIGUSR2 мастеру
```

Указатель в KV `WAF_DESIRED/policy/haproxy-conf` (тема `waf.desired.haproxy`):

```json
{
  "v": 1,
  "kind": "haproxy-conf",
  "rev": 4,
  "sha256": "sha256:…",
  "cfg": "global\n    maxconn 4096\n…"
}
```

`sha256` — хеш текста `cfg`; агент сверяет его до `haproxy -c` (целостность
доставки), контроллер — с пульсом (сходимость).

## Что настраивается

Источник — таблица `haproxy_settings`, одна строка на пространство. Пустой
документ компилируется в поставочный конфиг стенда — тот же, что bootstrap
образа: первая рассылка без правок не меняет поведение трафика.

| Секция | Что печатает |
| --- | --- |
| Процесс | `maxconn`, `tune.bufsize`, резолвер Docker DNS |
| Таймауты | `timeout connect/client/server/http-keep-alive/tunnel` |
| Вход | `bind *:<port>` фронтенда |
| Кластер | `balance`, `option httpchk`, `http-check expect status`, `check inter` |
| Серверы | строки `server <имя> <адрес>:<порт>` backend'а; пусто — edge-01..3 |
| Статистика | `listen stats` и его порт |

Чего здесь нет: бутстрапа агента (адрес шины, пути, pidfile — окружение
контейнера, см. `agents/haproxy/Dockerfile`) и TLS балансировщика — когда
появится, сертификаты поедут ссылками `store:<uuid>` тем же конвертом, что у
nginx.

## Что делает нода

Агент — Go-процесс в контейнере haproxy (по образцу `agents/redis`), бинарь
haproxy ему нужен тот же, что держит трафик, поэтому он не сайдкар.

1. Watch KV; первым событием приходит текущее поколение — нода, поднявшаяся
   после раскатки, применяет его сразу.
2. Сверить `sha256` текста.
3. Записать кандидат `haproxy.cfg.next`, прогнать `haproxy -c -f`.
   Провал — боевой файл не трогать, `apply_failed` в пульсе, кандидат
   остаётся на диске как улика.
4. Подменить файл, дождаться готовности мастера и послать ему SIGUSR2
   (`-W`): тот перечитывает конфиг и поднимает нового воркера, не разрывая
   соединений.

До первого поколения нода живёт на bootstrap-конфиге из образа
(`agents/haproxy/entrypoint.sh`) — он повторяет исторический статичный
`deploy/haproxy/haproxy.cfg`.

### Готовность мастера

Свой обработчик SIGUSR2 мастер ставит последним шагом загрузки, а до того
сигнал ему смертелен или теряется (haproxy 3.0.26, проверено на образе стенда):

| Стадия мастера | SIGUSR2 | Исход |
| --- | --- | --- |
| разбор конфига | по умолчанию | мастер умирает, код 140 |
| pidfile записан, цикла ещё нет | заблокирован и игнорируется | reload молча пропадает |
| цикл мастера | перехвачен | reload |

Та же загрузка повторяется на каждом reload: мастер перезапускает себя
(`execvp`) с заблокированными сигналами. Поэтому «pidfile есть, `kill -0`
проходит» — ещё не готовность. Агент ждёт, пока SIGUSR2 появится в
перехваченных сигналах мастера (`SigCgt` в `/proc/<pid>/status`), до 15 с.

Не дождался — `apply_failed` и повтор с отступом 1, 2, 4 … 30 с, пока не
пройдёт или не придёт новая ревизия. Ждать новой рассылки нельзя: `send` той
же ревизии идемпотентен по хешу файла и в KV ничего не кладёт. Отказ
`haproxy -c` не повторяется — это состояние файла, а не процесса.

pidfile прошлого запуска entrypoint удаляет до старта мастера: файл лежит в
слое контейнера и переживает `docker compose restart`, а pid мастера на новом
старте другой. Номер поднятого мастера entrypoint передаёт агенту
(`WAF_HAPROXY_MASTER_PID`); pidfile с другим номером агент считает чужим.

## Пульс и сходимость

Кадр присутствия — `WAF_STATUS.service.haproxy.<id>`, `kind=service
name=haproxy`: балансировщик — служба контура, не нода nginx и не инспектор.
Сверх обычного сервисного кадра едет секция `conf` — применённое поколение,
форма та же, что `agent_conf` у ноды:

```json
{ "conf": { "rev": 4, "sha256": "sha256:…", "apply": "ok" } }
```

`ready` кадра — жив ли мастер haproxy (процесс из pidfile есть и не зомби), а
не сам агент. Готовность к сигналу строже и в `ready` не входит: на время
reload мастер жив, но сигнал не примет, и лампа не должна мигать на каждом
перечитывании.

Канал `haproxy` в реестре сходимости
(`controller/src/convergence/channels.ts`) находит
потребителей по имени сервиса; полоса на `/config/haproxy` и лампа в шапке
работают тем же механизмом, что у остальных каналов
(`docs/config-convergence.md`).

## API контроллера

| Метод | Назначение |
| --- | --- |
| `GET /api/<scope>/haproxy` | Черновик настроек, `sha256` собранного файла |
| `PUT /api/<scope>/haproxy` | Сохранить черновик, не публикуя |
| `GET /api/<scope>/haproxy/preview` | Файл, который уедет на `send`, текстом |
| `POST /api/<scope>/haproxy/send` | Собрать файл, посчитать хеш, опубликовать указатель |
| `GET /api/<scope>/haproxy/desired` | Ревизия и хеш, стоящие на флоте |
