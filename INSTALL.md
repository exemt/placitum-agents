# Установка

Три процесса, три разных повода поставить.

## redis: наблюдатель экземпляра

Ставится по одному на экземпляр Redis. На контуре их два — обменник и внутренний, — и агенты
различаются только адресом и именем: по имени их и различает страница «Состояние».

| Переменная | По умолчанию | Что |
| --- | --- | --- |
| `WAF_NATS_URL` | `nats://nats:4222` | шина: кадр присутствия и журнал |
| `REDIS_URL` | `redis://redis:6379` | за каким экземпляром смотреть |
| `WAF_REDIS_NAME` | `redis` | имя в кадре: `WAF_STATUS.store.redis.<имя>` |
| `WAF_DATA_DIR` | `/var/lib/waf/agent` | состояние агента |
| `WAF_REDIS_AGENT_LOG` | `info` | уровень журнала |

```yaml
  redis-agent:
    image: placitum/agents-redis
    environment:
      WAF_NATS_URL: nats://nats:4222
      REDIS_URL: redis://redis:6379
      WAF_REDIS_NAME: redis
  redis-internal-agent:
    image: placitum/agents-redis
    environment:
      WAF_NATS_URL: nats://nats:4222
      REDIS_URL: redis://redis-internal:6379
      WAF_REDIS_NAME: redis-internal
```

## s3: наблюдатель архива

Один на установку. Кроме наблюдения делает одну полезную вещь: **заводит бакеты архива**, если
их нет.

| Переменная | По умолчанию | Что |
| --- | --- | --- |
| `WAF_NATS_URL` | `nats://nats:4222` | шина |
| `S3_ENDPOINT` | `http://minio:9000` | адрес хранилища |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | — | реквизиты |
| `S3_REGION` | `us-east-1` | регион |
| `S3_BUCKET` | `waf-bodies` | основной бакет в кадре присутствия |
| `S3_ENSURE_BUCKETS` | — | список через запятую: их агент создаст, если нет |
| `WAF_S3_NAME` | `s3` | имя в кадре: `WAF_STATUS.store.s3.<имя>` |

Реквизиты здесь переменными, а не файлом, — это осознанное исключение: агент не держит секретов
контура, а ключи хранилища и так знает соседний процесс. Для установки, где это неприемлемо,
используйте секреты своей платформы оркестрации.

## haproxy: узел балансировщика

Не наблюдатель, а нода: haproxy и агент в одном контейнере, конфигурацию присылает контроллер,
агент применяет её через `haproxy -c` и `SIGUSR2` мастеру.

| Переменная | По умолчанию | Что |
| --- | --- | --- |
| `WAF_NATS_URL` | `nats://nats:4222` | шина: поколение конфигурации и пульс |
| `WAF_HAPROXY_BIN` | `haproxy` | бинарь, которым проверяется и исполняется конфиг |
| `WAF_HAPROXY_CFG` | `/usr/local/etc/haproxy/haproxy.cfg` | куда агент пишет поколение |
| `WAF_HAPROXY_PIDFILE` | `/var/run/waf/haproxy.pid` | pid мастера для сигнала |
| `WAF_DATA_DIR` | `/var/lib/waf/agent` | состояние: применённое поколение |
| `WAF_HAPROXY_AGENT_LOG` | `info` | уровень журнала |

Порядок в контейнере обратный обычному: сначала поднимается haproxy с заглушкой, потом агент —
перезагружать нечего, пока мастер не запущен.

## Проверка

У всех троих проверка одна: кадр присутствия на шине.

```sh
nats sub 'WAF_STATUS.store.>' --count 2
nats sub 'WAF_STATUS.node.>' --count 1     # haproxy
```

В панели они видны на странице «Состояние»: Redis по имени экземпляра, S3 по бакетам, haproxy —
как нода с поколением и признаком применения.

## Грабли

- **Два агента Redis — два имени.** Одинаковое `WAF_REDIS_NAME` у обоих означает, что на
  странице они схлопнутся в один, и понять, у какого экземпляра кончилась память, будет нельзя.
- **`S3_ENSURE_BUCKETS` пуст** — агент ничего не создаёт. Архив тогда начнёт писать в
  несуществующий бакет и ответит ошибкой на первом же объекте.
- **Агент haproxy не сайдкар.** Вынести его в отдельный контейнер нельзя: проверка конфига
  требует того же бинаря, что держит трафик.
