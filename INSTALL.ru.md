# Установка

[English](INSTALL.md) · Русский

Три процесса, три разных повода поставить. Агенты Redis и S3 обычно ставит `placitum-core`; узла
haproxy в установке пока нет.

## redis: наблюдатель экземпляра

По агенту на экземпляр Redis. В обычной установке их два — обменник и внутренний, — и агенты
различаются только адресом и именем: по имени их и различает страница состояния в панели.

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `WAF_NATS_URL` | `nats://127.0.0.1:4222`; в образе `nats://nats:4222` | шина: кадр присутствия и журнал |
| `REDIS_URL` | `redis://127.0.0.1:6379`; в образе `redis://redis:6379` | за каким экземпляром смотреть |
| `WAF_REDIS_NAME` | `redis` | имя в кадре |
| `WAF_DATA_DIR` | `/var/lib/waf/agent` | состояние агента: файл `agent.id` |
| `WAF_HEARTBEAT_EVERY` | `4s` | период кадра |
| `WAF_REDIS_AGENT_LOG` | `info` | уровень журнала |

```yaml
  redis-agent:
    image: placitum/agents-redis
    environment:
      WAF_NATS_URL: nats://nats:4222
      REDIS_URL: redis://redis:6379
      WAF_REDIS_NAME: redis
  redis-internal-agent:
    image: placitum/agents-redis
    environment:
      WAF_NATS_URL: nats://nats:4222
      REDIS_URL: redis://redis-internal:6379
      WAF_REDIS_NAME: redis-internal
```

В кадре — ответ на `PING` и числа из `INFO`: версия, роль, занятая и предельная память, политика
вытеснения, ключи, ключи со сроком, вытеснения, попадания, промахи, клиенты, аптайм. Если Redis
недоступен, кадр всё равно уходит: контроллер видит деградацию хранилища, а не пропажу агента.

## s3: наблюдатель архива

Один на установку. Кроме наблюдения делает одну полезную вещь: **заводит бакеты архива**, которых
ещё нет.

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `WAF_NATS_URL` | `nats://127.0.0.1:4222`; в образе `nats://nats:4222` | шина |
| `S3_ENDPOINT` | `http://127.0.0.1:9000`; в образе `http://minio:9000` | адрес хранилища |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | `waf`, `wafwafwaf` | реквизиты |
| `S3_REGION` | `us-east-1` | регион подписи |
| `S3_BUCKET` | `waf-bodies` | бакет, который проверяется для кадра |
| `S3_ENSURE_BUCKETS` | значение `S3_BUCKET` | бакеты через запятую, которые создать при старте |
| `WAF_S3_NAME` | `s3` | имя в кадре |
| `WAF_DATA_DIR` | `/var/lib/waf/agent` | состояние агента: файл `agent.id` |
| `WAF_HEARTBEAT_EVERY` | `4s` | период кадра |

Реквизиты здесь переменными, а не файлом, — это осознанное исключение: агент не держит секретов
установки, а ключи хранилища и так знает соседний процесс. Где это неприемлемо, используйте
секреты своей платформы оркестрации.

С MinIO в кадре есть ещё число объектов, занятые байты и темп запросов из его admin API и метрик;
у обычного S3 без них остаётся только проверка бакета.

## haproxy: узел балансировщика

Не наблюдатель, а узел: haproxy и агент в одном контейнере. Контроллер публикует собранный
`haproxy.cfg` в документе KV `policy/haproxy-conf`; агент сверяет хеш, прогоняет `haproxy -c`,
подменяет файл и перезагружает haproxy через CLI мастера.

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `WAF_NATS_URL` | `nats://127.0.0.1:4222`; в образе `nats://nats:4222` | шина: конфигурация и кадр присутствия |
| `WAF_HAPROXY_BIN` | `haproxy` | бинарь, которым проверяется и исполняется конфиг |
| `WAF_HAPROXY_CFG` | `/usr/local/etc/haproxy/haproxy.cfg` | куда агент пишет конфиг |
| `WAF_HAPROXY_MASTER_SOCK` | `/var/run/waf/master.sock` | сокет CLI мастера, ключ `-S` у haproxy |
| `WAF_HAPROXY_PIDFILE` | `/var/run/waf/haproxy.pid` | pid мастера: жив ли haproxy |
| `WAF_DATA_DIR` | `/var/lib/waf/agent` | состояние агента: файл `agent.id` |
| `WAF_HAPROXY_AGENT_LOG` | `info` | уровень журнала |

Порядок в контейнере обратный обычному: сначала поднимается haproxy на стартовом конфиге, потом
агент — перезагружать нечего, пока мастер не запущен. Вне образа запускайте haproxy так же: `-W`,
`-S` на `WAF_HAPROXY_MASTER_SOCK` и `-p` на `WAF_HAPROXY_PIDFILE`.

`ok` в кадре появляется, только когда мастер подтвердил, что новый worker запущен. Провал
`haproxy -c` не трогает рабочий файл. Файл, который прошёл проверку, но не загрузился, например
из-за занятого порта, остаётся на месте, а трафик держит старый worker. В обоих случаях в кадре
`apply_failed`, а в журнале агента — сообщения haproxy. Агент пробует ревизию снова через секунду,
потом с паузой, которая удваивается до 30 секунд, пока она не загрузится или не придёт более новая:
порт, который освободил другой процесс, не требует новой рассылки.

После подтверждённой перезагрузки агент пишет хеш файла в `haproxy.cfg.loaded` рядом с ним. Если
при рестарте агента haproxy уже исполняет нужную ревизию, агент его не перезагружает.

## Проверка

У всех троих проверка одна: кадр присутствия на шине.

```sh
nats sub 'WAF_STATUS.store.>' --count 2
nats sub 'WAF_STATUS.service.haproxy.>' --count 1
```

В панели они видны на странице состояния: Redis по имени экземпляра, S3 по бакетам, haproxy — с
применённой ревизией конфигурации.

## Грабли

- **Два агента Redis — два имени.** С одинаковым `WAF_REDIS_NAME` они схлопнутся в одну карточку,
  и понять, у какого экземпляра кончилась память, будет нельзя.
- **Перечислите все бакеты архива в `S3_ENSURE_BUCKETS`.** По умолчанию создаётся только
  `S3_BUCKET`, и архив ответит ошибкой на первом объекте в несуществующий бакет.
- **Агент haproxy не сайдкар.** Вынести его в отдельный контейнер нельзя: проверка конфига требует
  того же бинаря, что держит трафик.
- **Незагрузившийся конфиг остаётся рабочим файлом.** Если haproxy перезапустится раньше, чем придёт
  исправная ревизия, он стартует с этого файла и упадёт так же. Устраните причину, например
  освободите порт, и перезапустите контейнер: агент перезагрузит haproxy и подтвердит файл.
